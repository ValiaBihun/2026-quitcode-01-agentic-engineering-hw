# Vibe-нотатки — Воркшоп 1

**Застосунок:** Судоку (6x6, цифри 1–6) на Next.js 16 (App Router) + Porsche Design System v4.
**Інструмент:** Claude Code (Sonnet 5).
**Формат роботи:** ланцюжок із 7 користувацьких промптів-ітерацій в одній сесії (без очищення контексту між ними).

## 1. Що вийшло з першого промпту, а що ні

- **Вийшло одразу:** перший промпт ("Next.js, simple Sudoku game, Porsche Design System v4")
  дав повністю робочий каркас — генератор пазлів із гарантованою єдиністю розв'язку,
  валідацію конфліктів, PDS-компоненти — з першої спроби. Це стало можливим тільки
  тому, що перед написанням коду агент витратив окремий крок на дослідження (звірка
  актуальних версій `next`/`react`/`@porsche-design-system/components-react` через
  `npm view`, читання офіційного гайду інтеграції PDS+Next.js) і зафіксував це в плані
  до старту імплементації.
- **Не вийшло з першого разу:** `@import "@porsche-design-system/components-react";`
  (без розширення `/index.css`) у `globals.css` — Turbopack мовчки не резолвив цей
  imports, і всі глобальні стилі PDS (шрифти, кольори, скидання) просто зникали, хоча
  самі компоненти коректно гідратувались (`class="hydrated"` було в DOM). Знайшли
  через порівняння вмісту скомпільованого CSS-чанка з очікуваним — вигляд сторінки був
  "ніби не той браузер завантажив CSS".
- **Не вийшло з першого разу:** фон сторінки та кольори кнопок не відповідали
  дизайн-системі, доки не активували правильний механізм PDS — клас
  `.scheme-light-dark` на `<html>`, який вмикає CSS `color-scheme`. Без нього всі
  токени на основі `light-dark()` (включно з фоном канви) не мали способу дізнатися,
  яку тему показувати, і компоненти/кастомний CSS розходились візуально.
- **Не вийшло з першого разу:** ESLint зловив реальну помилку
  (`react-hooks/set-state-in-effect`) одразу після додавання таймера — виклик
  `setState` синхронно в тілі ефекту. Виправили, перенісши скидання таймера в сам
  редюсер (частина дії `NEW_GAME`), залишивши ефект лише для підписки на `setInterval`.
- **Вийшло без сюрпризів:** перехід дошки з 9x9 на 6x6 (боксами 2x3) — завдяки тому,
  що вся математика судоку від самого початку була винесена в іменовані константи
  (`SIZE`, `BOX_ROWS`, `BOX_COLS`), а не захардкоджена як "9"/"3".

## 2. Де агент спіткнувся і як його розвернули

- **Найбільший архітектурний злам:** запит "Clicking on a cell must highlight its
  row/column/block" + "Pencil mode adds multiple marks in one cell" означав, що
  кожна клітинка більше не могла бути простим `<input>` (там неможливо показати
  6 дрібних нотаток одночасно і неможливо мати окреме поняття "виділена клітинка"
  для підказки). Довелось повністю переписати `SudokuCell` на `<button>` з обробкою
  `onKeyDown`. Побічний ефект, який агент сам виявив і виправив без окремого
  прохання: на дотикових пристроях зник спосіб вводити цифри (нативна `inputMode
  ="numeric"` клавіатура зникла разом з `<input>`), тож додали окрему екранну
  цифрову панель (`NumberPad`), щоб не втратити зручність на мобільних.
- **Хибні тривоги під час верифікації:** кілька разів у консолі браузера з'являлись
  "привиди" — помилки на кшталт `Cannot read properties of undefined` після гарячого
  перезавантаження (Fast Refresh) під час редагування файлів. Розворот: замість того,
  щоб одразу правити код, спочатку перевірили це через повне перезавантаження вкладки
  (`navigate`, а не просто F5 — F5 у цьому середовищі один раз відновив стан із
  bfcache замість справжнього перезавантаження) і підтвердили, що помилка не
  повторюється на чистому старті — отже, це був артефакт інструменту розробки, а не
  баг у коді.
- **Підозра на баг генератора:** після однієї серії редагувань "medium" складність
  один раз показала 20 підказок замість очікуваних 16. Замість здогадок написали
  окремий Node/`tsx`-скрипт, який імпортує саме той `lib/sudoku.ts`, що йде у
  продакшн, генерує пазли для всіх складностей і перевіряє єдиність розв'язку та
  точну кількість підказок. Скрипт підтвердив, що генератор завжди коректний
  (16/32→16, 20 було залишком застарілого HMR-стану), і після цього видалили
  тимчасовий скрипт з репозиторію.

## 3. Числа

- **Промптів-ітерацій користувача в сесії:** 7 (клонування репо → пояснення репо →
  створення застосунку → зміна дошки на 6x6 → фон/таймер/кнопки → стан гри
  (пауза/олівець/підказка/виділення) → цей коміт+Pages+PR).
- **Файлів у застосунку:** ~20 (компоненти `.tsx` + CSS-модулі + `lib/sudoku.ts` +
  конфігурація), плюс окремий `.claude/launch.json` для локального прев'ю.
- **Цикли перевірки:** щонайменше 5 повних проходів `npm run build` + `npm run lint`
  (усі — чисті, 0 помилок на момент здачі), один самостійний скрипт-верифікатор
  алгоритму судоку (одноразовий, видалений після використання), і десятки скріншотів
  у браузері для перевірки кожної нової механіки (виділення, олівець, підказка,
  пауза/резюм, фон, таймер).
- **Токени/вартість сесії:** агент **не має** прямого програмного доступу до точної
  суми у доларах зсередини сесії — цю цифру потрібно звірити самостійно командою
  `/cost` у Claude Code (або на екрані використання інструменту). За внутрішнім
  лічильником бюджету токенів цієї сесії (`total_tokens left`, який періодично
  скидається через стиснення контексту, тож накопичувальну суму за ним точно
  порахувати не можна) — сесія охопила помітний обсяг: багаторазові виклики
  `WebFetch`/`WebSearch` для документації PDS і Next.js, читання файлів пакета PDS
  (`skills/pds-knowledge-react`), і десятки раундів взаємодії з браузером для
  візуальної перевірки. Свідомо не наводимо тут вигадану цифру в доларах — краще
  чесно вказати, де її знайти, ніж дати неточне число.

## 4. Спостереження на майбутнє

1. Документацію для AI-агентів, яку сам пакет носить у собі (наприклад
   `node_modules/@porsche-design-system/components-react/skills/pds-knowledge-react`
   або `node_modules/next/dist/docs`), варто читати **до** першого рендеру, а не
   після першої невдалої спроби — вона версійно-точна для встановленого пакета, на
   відміну від публічної документації в інтернеті, яка описує "останню" версію і
   може розходитися з тим, що реально встановлено.
2. Складні UI-стани (idle/playing/paused, режим олівця, виділена клітинка) варто
   одразу проєктувати як єдину машину станів в одному редюсері, а не додавати по
   одному `useState`/`useEffect` — це б одразу зняло питання "де саме скидати
   таймер", яке коштувало одного зайвого циклу виправлення лінтера.
3. Наскрізні сценарії (повне розв'язання судоку, перемога) варто одразу
   автоматизувати невеликим JS-скриптом у браузері (програмно розв'язати пазл і
   заповнити дошку), а не покладатися лише на ручні кліки — це і швидше, і надійніше
   виявляє реальні регресії після великих архітектурних змін (наприклад, коли
   клітинки перетворились з `<input>` на `<button>`).
